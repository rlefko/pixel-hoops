# Performance Conventions

The hard-won rules from nine performance passes (#80, #81, #88, #90, #109, #111, #112, #114, #122). Every rule below was earned by a real, verified defect: the "why" lines describe mechanics confirmed in this codebase or in native library source, not folklore. Treat this file as the source of truth for performance review; the `perf-review` skill walks it, and the pre-commit performance agent checks every change against it. This doc owns the battery, CPU, and responsiveness mechanics; how a change should look, sound, and land lives in `docs/feel-conventions.md` (the `feel-review` skill).

## Prime directive

Battery, CPU, and tap-to-paint responsiveness are first-class product constraints, equal to gameplay design. Pixel Hoops should be a lightweight, flight-friendly game: no heat, no drain, no dead taps. Two standing consequences:

1. The simulator and the coach lineup search are pure, seeded, and deterministic. Performance work on them must be provably output-identical, pinned by golden tests recorded before the change.
2. Presentation work must stay behavior-close and interactive-first: it is always acceptable to remove invisible work, and never acceptable to trade a tap's responsiveness for a flourish.

## 1. Animation and motion

- **Every infinite `withRepeat` loop gates on effective `reducedMotion` AND a runtime pause.** Effective reduced motion is `userSetting || lowPowerMode` (from `useFeelSettings`; Low Power Mode forces the whole juice layer down, #90). The runtime pause is `useIdle` (via `useHubBackdrop` on hub screens) for screens the player stares at, or a condition like `!hot` / `!isReachable` for elements that only sometimes animate. A loop that checks only reducedMotion is a defect (#80, #88).
- **Reuse the canonical pulse helpers** in `src/feel/usePulse.ts` (`useGlowPulse`, `useBobPulse`, `useScalePulse`); they hold steady under `reducedMotion || paused` and cost zero loops while paused. Do not hand-roll a repeat loop.
- **Never add always-on work to the live game watch** (`CourtView`, `PlayByPlayFeed`). The watch is event-driven, not per-frame; that property is what makes the whole app cheap (#80).
- **Pure-atmosphere flourishes also gate behind the `arcadeExtras` setting.**
- **Off-screen screens freeze** (`freezeOnBlur` on the stacks, #88). Do not rely on a blurred screen's loops being cheap; rely on them being frozen.
- **Never animated-scroll a screen the player is about to tap.** During an animated `scrollTo`, React Native delivers a tap to the scroll-canceller, not to the child Pressable: the first tap silently stops the scroll and the player reads it as a stall (#114). Land in position instead (the run map uses a `useLayoutEffect` ref jump before the first frame paints). Do not use a controlled `contentOffset` prop (re-renders can snap a manually scrolled view back) and do not set `canCancelContentTouches={false}` (it breaks drag-to-scroll started on child tiles).
- **Heavy screen mounts land behind the wipe's full cover.** `TransitionProvider.run` holds the cover until the destination's commit paints (`afterCommit`, double `requestAnimationFrame`); the reveal must never race a heavy mount (#111). Mount work extends the covered dwell 1:1 on top of the designed double-rAF + label hold (nothing is "absorbed"); `useSlowMountWarning` budgets a hub mount at one hold's worth (80ms) of added dwell.
- **`afterCommit` covers exactly ONE commit; a multi-commit cascade behind one wipe must declare settlement.** The auto-skipped championship dispatches through a placeholder commit before the summary lands; revealing after the first commit dissolved onto "FINAL..." mid-cascade (#122). A `ceremony` whose action cascades returns a promise that resolves when the destination phase is reached (RunScreen's settle waiters); the provider holds the cover until it settles, with a capped timer (built only on that path, cleared when the action wins) so a broken waiter can never strand the cover. Celebration beats then anchor to the reveal actually completing, not the mount, so they land visibly instead of under the mosaic.
- Verify on any diff: `git diff origin/main... | grep -E '^\+.*(withRepeat|scrollTo)'` and confirm each hit's gates.

## 2. Audio

- **Create players only through `src/feel/audioPlayers.ts`, never `createAudioPlayer` directly.** The factory passes a quiet `updateInterval`: on Android every expo-audio player runs an unconditional main-thread wakeup loop at that interval for its entire lifetime, even paused (the 500ms default across ~37 resident players cost ~74 wakeups per second, #109). It also owns `ensureAudioMode`, which must complete before any player exists.
- **Load lazily, gate everything.** Music beds load per declared context through `music.ts`'s desired/applied `sync()` reconciler; boot loads only the menu bed, a run loads its one theme plus the energy layer, and nothing loads or plays while music is off, backgrounded, or in Low Power Mode (#109).
- **Bound rapid cues; every `play()` is expensive.** One SFX shot is 3-4 native calls plus observer re-registration inside expo-audio's `play()`. Rapid-fire cues take per-name cooldowns from `RAPID_CUE_COOLDOWN_MS` in `src/feel/soundPolicy.ts` (taps and toggles 45ms; count ticks 80ms so a capped 600ms tally sings ~8 notes, matching TickCounter's 8-step pitch ladder; tests pin these couplings, #112).
- **Skip no-op native writes.** Both `music.ts` and `audio.ts` keep `lastVolume` caches and only write a player's volume when the computed value changed (#109, #112).
- **Volume tweens exist only while a fade runs and cancel on deactivate.** Backgrounding halts all tweens and resets the duck factor; a silent bed costs zero bridge calls during a duck (#109).
- **Never seek-then-play on the shot hot path; park players at zero when they finish.** On iOS, `play()` and `setPlaybackRate()` are sync JSI Functions but `seekTo()` is an AsyncFunction on a separate native queue, so `seekTo(0); play()` races: the play executes against the OLD position, and since expo-audio never auto-rewinds a finished player (it parks at end-of-file), the raced shot is silent or partial — the audible "stutter" under rapid upgrade taps (#122, verified in `AudioModule.swift`). `audio.ts` re-parks each player at 0 on its `didJustFinish` event (emitted via NotificationCenter/ExoPlayer callback regardless of the 60s `updateInterval`), pausing FIRST — on Android, ExoPlayer keeps `playWhenReady` at `STATE_ENDED`, so a bare seek out of it audibly auto-replays. Only a busy reuse (pool exhausted mid-shot, or state unknown after backgrounding) takes the explicitly ordered `seekTo(0).then(play)`.
- **Keep the audio session claimed while foregrounded (`keepAudioSessionActive: true` in the factory).** expo-audio's default deactivates the AVAudioSession ~100ms after any player finishes with nothing else playing, and the next `play()` re-activates it synchronously ON THE JS THREAD — with music off, that put a session round-trip inside every SFX shot (#122). The flag eliminates the deactivation and degrades the (unconditional) per-play `setActive(true)` to a cheap redundant call; backgrounding still releases the session via `setAudioActive(false)`.
- **Pool sizes are a duration-and-rate invariant, checked at bake time.** A cooldown-listed cue must satisfy `wavDuration / slowestJitterRate <= cooldown x pool`, or the round-robin hands back a player still audibly mid-shot; `gen:sfx` fails the bake on a violation and `recipes.test.ts` pins it (#122). Cues shared across sources (whoosh: navigation + celebration beats + watch juice) need pool headroom for cross-source collisions even when one source alone is serialized.

## 3. Reducers and the tap path

- **Reducer actions on tap paths are O(1).** The run machine executes synchronously inside React dispatch, so a slow action blocks the very tap that fired it. Heavy derived work belongs in a pure exported `compute*` function scheduled after the tap's frame commits (`InteractionManager.runAfterInteractions`), landing through a guarded sentinel action. Follow the `computeCoachRec` / `setCoachRec` pattern in `src/game/run-machine.ts` and `src/hooks/useRun.ts`: `undefined` means not computed yet, `null` means resolved, and the reducer refuses stale or duplicate landings (#111). The biggest catch to date: `enterGame` ran the ENTIRE game simulation inside the dispatch — the app's largest synchronous JS block, on the TIP OFF tap, felt on a release build (#122); it now consumes a `pendingGame` precomputed in pregame idle (`computeGameSim` / `setGameSim`, keyed on every sim input mutable during a pregame, with the identical sync sim as fallback so determinism is a test-pinned identity).
- **An effect that computes O(collection) on a commit frame is a reducer violation wearing a hook.** The run-end settle (acquisitions preview, bounty gacha, daily grants, full collection merge) ran synchronously in a `useEffect` on the same frame the champion celebration mounted (#122). Heavy settle-style work extracts into a pure module (`src/game/run-settle.ts`), runs one `InteractionManager` task later behind the held ceremony cover, and keeps an idempotent tap-time fallback (`ensureSettled`) so exit handlers always read settled data; anything a later tap routes on must come from the settle's RETURNED outputs, never a render-baked closure. Defer only where a cover or celebration protects the frame — the loss path settles inline because its coverless summary would visibly shift when the strips popped in.
- **Keep the slow-action warning wired.** `withSlowActionWarning` (`src/game/dev-timing.ts`) wraps the run reducer in dev and warns on any action at or over 16ms. When touching the reducer, run a hard S/S+ run in dev and watch for `[run] slow action` lines. (A `skipToResult` warning is expected on skipped boss wins: it fires from an effect, not a tap, and composes two actions deliberately.)
- **Persistence is debounced, never on a tap.** All stores write through the shared debounced writer (`src/storage/debouncedWriter.ts`), which coalesces bursts and flushes on background (#81). Never `JSON.stringify` a store synchronously in a tap handler or reducer. Large re-derivable blobs also never enter a save's value: `active-run.ts` strips `model.game` AND any pregame `pendingGame`, and phase-capturing reducers (`openLineupBuilder`, `openBag`) strip `pendingGame` from the `returnTo` they store, or every lineup/bag auto-save stringifies a full SimResult (#122).

## 4. React render hygiene

- **Virtualize long card lists.** Locker, roster, arcade loadout, and draft pool use `FlatList`; hundreds of mounted `PlayerCard`s was the app's worst freeze (#81).
- **Memoize repeated SVG-heavy tiles and keep their callbacks identity-stable.** `MapNodeTile` is `React.memo`'d; `useRun` splits its actions into dispatch-only closures (memoized once; `dispatch` is stable) and home-roster closures, so `actions.chooseNode` never churns on a coin bank (#111). New run actions go in the right group.
- **A spray-tap list re-renders one row per tap, not the window.** The locker upgrade tap re-rendered every visible row (~450 elements + fresh closures) because `onUpgrade` closed over the live store and the row took the whole store object (#122). The pattern: read the store through a ref inside a `useCallback` (the `onPin` precedent), and hand each row only identity-stable slices — the player object and ledger entry that `applyUpgrade` structurally shares, plus derived cross-row state packed into a value type (`affordMask`, a bitmask, in `src/game/upgrades.ts`) so a row's memo compares one number instead of the wallet. Residual per tap: one cell-level renderItem + memo-compare pass per mounted row, which is the accounted cost, not a leak.
- **Narrow `useMemo` deps to what the computation reads.** The pregame screen memoizes team builds and identities on the core/roster inputs, so a phase-only dispatch (like the coach scout landing) rebuilds nothing (#111).
- **Count-ups stay leaf-local and quiet.** Counter state lives in leaf components (one `Text`); `useCountUp` commits only real integer changes and stops its rAF loop the moment the display lands on the target (#112). Do not reintroduce per-frame setState.
- **No cargo-cult memoization.** Memoization has its own cost; it is only justified where re-renders are frequent or the subtree is heavy. Documented rejections that should stay rejected without new evidence: memoizing `BoxScoreView`/`LineupBoard` (never mounted during the feed), conditionally mounting `FlashOverlay`, converting `useCountUp` to a worklet, court rasterization, `expo-image` for bundled logos, and the `tendencyFor` sim cache (#88, #90). #122's additions: shrinking the wipe cell grid (its per-frame worklet cost measured within budget; the felt stutter was mount/JS contention, not the overlay), shortening SFX cooldowns (tick=80ms is pinned to the count-up pitch ladder; dropped over-cadence ticks are correct craft), micro-optimizing teach-ledger/hub-delta focus work (O(dozens) per focus = noise), and cutting `initialNumToRender` in the locker (the StaggerIn fill batch would read as a late second cascade wave; revisit only if the mount tracer shows it over budget).

## 5. Optimization discipline

- **Golden tests first, and never regenerate them for performance work.** Before optimizing deterministic code, record characterization tests pinning exact outputs (`src/game/__tests__/golden-master.test.ts` for the sim, `src/game/__tests__/coach-reco-golden.test.ts` for the lineup search). They may be regenerated only for an intentional gameplay change.
- **Exactness arguments, not vibes.** A pruning or reordering optimization needs a proof sketch against the real code: monotone terms, strict-inequality tie-breaking, no floating-point regrouping (addition is not associative). The coach-search pruning in `src/game/coach-reco.ts` is the model (#111).
- **Verify claimed native costs in source before fixing.** The decisive facts in these passes came from reading `node_modules` internals (expo-audio's per-player wakeup loop and observer churn, ScrollView's tap-cancel semantics), not from assumptions. A fix aimed at an unverified cost is a guess.
- **Account costs structurally**: calls x frequency x thread. "~95 team builds per tap on the JS thread" decides priorities; "it feels slow" does not.
- **Calibrate symptoms to the build type.** Dev-mode JS runs roughly 10-50x slower than release; a release-build stall implicates native-side work (mounts, animations, scroll semantics) more than pure JS math. A stall felt on the newest iPhone in a release build means the work is genuinely large — go hunting for a synchronous block, not a micro-optimization (#122's sim-in-reducer).
- **Use the standing dev tracers before and after any responsiveness fix.** `[nav] slow transition` (TransitionProvider + `src/navigation/transition-timing.ts`, warns when commit+paint eats 100ms of covered dwell, with any ceremony hold reported separately), `[nav] slow mount` (`useSlowMountWarning`, 80ms budget per hub screen), `[run] slow action` (16ms reducer budget), and `[sfx] slow shot` (4ms native-dispatch budget, plus `devSfxShotCounts()` for the fast/busy/dropped split). A claimed win should move one of these lines; new hub screens add the one-line mount warning (#122).
- **Prefer removing work over spreading it, and document rejections.** Every pass shipped a "deliberately not done" list with reasons; keep that honesty. An optimization that cannot show its win structurally should not ship.

## 6. Known debts

- `PlayerCard` glow loops on LEGENDARY and zenith cards run with no idle pause on long-lived screens (roster, locker, lineup builder). Ordinary cards are already paused (`paused: !legendaryGlow` on the name glow, `paused: !animated` on the tier badge), so this bites only when a legendary or zenith card is visible; fixing it properly needs a `paused` prop threaded through ~20 mount sites (recorded as future work in #112).

## Review checklist

For any diff, check in order:

1. New `withRepeat` or animation loop: gated on effective reducedMotion AND a runtime pause? Uses the pulse helpers?
2. New `scrollTo` or scroll behavior: can it eat a tap the player is about to make?
3. New audio: created via the factory? Cue bounded? Loads gated on enabled/foreground/low-power? No `seekTo` before `play` on a hot path (the finish listener owns rewinds; only a busy reuse awaits the seek)? A new or lengthened cooldown cue passes the bake's duration/pool invariant?
4. New reducer work: O(1) on tap paths? Heavy derivation moved behind a sentinel action? No `simulate*` or O(collection) helper called inside a dispatch OR inside an effect that runs on a commit frame the player is watching?
5. New synchronous persistence, `JSON.stringify`, or unbounded loop on an interaction path? Any large re-derivable blob (a SimResult, a built Team) entering a persisted phase, including one captured into a `returnTo`?
6. New list of cards/tiles: virtualized or memoized with stable props? A spray-tappable row's memo inputs identity-stable across an unrelated save?
7. Touches sim/coach-search math: golden tests recorded first and passing unchanged?
8. Any per-frame or per-event work added to the live watch?
9. New `ceremony(` call whose action cascades through more than one commit: does it return a settlement promise so the cover holds to the real destination? New hub screen: has the one-line `useSlowMountWarning`?
